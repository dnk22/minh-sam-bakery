# CMS session recovery

- A protected BFF 401 starts one shared browser refresh sequence. Other protected requests wait; successful recovery replays GET and pre-operation rejected mutations once, preserving method/body/abort signal. A mutation 401 after dispatch is ambiguous and must not be replayed automatically.
- Global native modal uses the existing CMS theme, a Zustand vanilla store and no retry/close buttons. Maximum three POST attempts total, immediate then 1s/2s backoff. Terminal 401/423/403 returns to login immediately; retryable 429/network/5xx/invalid response follows bounded backoff. Retry-After is forwarded from Backend where available; values above 30s end recovery instead of retrying earlier.
- Same-tab single flight and Web Locks + non-secret localStorage completion/scope metadata deduplicate concurrent cross-tab requests. Without Web Locks or storage support, cross-tab guarantees degrade; same-tab serialization remains. Login/logout take the same lock and invalidate the scope, preventing replay from a known old session.
- HttpOnly cookie policy, CSRF, token response validation and Backend API contracts are unchanged. On retries the BFF checks current cookie freshness and /me before rotating again, including after a previous rotation succeeded but /me failed. Temporary failures preserve cookies and use an explicit login error path to avoid login/refresh loops.
- Backend rotation after a lost response cannot be made fully idempotent by FE; Backend must support a rotation grace window or idempotency for that guarantee. A definitive Backend rejection clears cookies as before. Browser-only refresh coordination is not a distributed lock across devices.
- No proactive timer is introduced. Protected navigation continues to use /cms/session-refresh; the page and background API calls now share the same manager. Image tags/raw fetch that bypass the shared client do not automatically replay.

The source and mocked fetch tests are not a substitute for real Backend rotation/E2E.
